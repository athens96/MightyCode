# Tailscale 원격 워크스페이스

Mac이나 Windows 컴퓨터 두 대의 Mighty Code를 Tailscale로 이으면, 한쪽(클라이언트)에서 다른 쪽(호스트)의 워크스페이스를 열고 호스트에서 Claude Code·Codex·Antigravity와 명령을 실행한다. 파일과 CLI 로그인은 호스트에 그대로 있고, 프로젝트 파일을 복사하거나 동기화하지 않는다. 사용 안내는 도움말 [원격 연결 (Tailscale)](help/content/ko/remote.md)에 있다.

연결하면 호스트가 공유한 워크스페이스가 호스트에 열려 있는 에이전트 창 그대로 클라이언트 사이드바에 나타나고, 클라이언트에서 그 창을 계속 쓴다(아래 [그 컴퓨터의 창 그대로](#그-컴퓨터의-창-그대로-원격-미러), 2026-11-13 Mac·Windows). 그 전부터 있던, 클라이언트가 가진 창을 호스트에서 실행만 하는 방식([실행](#실행))도 그대로 쓴다.

2026-09-28 `e4f973b`에서 지웠다가 2026-10-17에 Mac에 다시 만들었고, Windows 앱에도 같은 프로토콜로 만들었다(아래 [Windows와 Mac↔Windows](#windows와-macwindows), [windows-parity.md](windows-parity.md)). 휴대폰은 릴레이로 Mac에 붙는 별도 기능이고([mobile-remote.md](mobile-remote.md)), 원격 워크스페이스를 휴대폰에 비추지 않는다.

## 화면

**설정 → 원격 연결** 탭. 0.5(Rust 앱)는 Mac·Windows가 같은 화면이다(`native/tauri/src-tauri/src/settings/remote.rs`; 아래에 남은 `…Swift`·`.cs` 이름은 은퇴한 0.4 앱의 참고 구현이다). 탭 안은 **이 컴퓨터 공유 | 다른 컴퓨터 연결 | 휴대폰** 세 탭이고, 고른 안쪽 탭은 앱이 도는 동안만 기억한다. 사이드바의 지구본(네트워크) 단추는 0.5.3에서 없어졌고, 사이드바 아래의 설정 단추로 설정을 열어 이 탭을 고르거나, 워크스페이스의 **창 추가** 메뉴의 **다른 컴퓨터 연결…**, 첫 화면(작업 현황)의 같은 단추로 연다.

- **이 컴퓨터 공유**: 공유할 로컬 워크스페이스를 고르고(기본은 앞에 있는 워크스페이스), 포트(기본 `43137`)를 정해 **공유 시작**. 공유 중에는 이 Mac의 Tailscale 주소(`주소:포트`)마다 한 줄과 연결 키가 **복사** 단추와 함께 보이고, 이 Mac에서 도는 원격 실행 수가 보인다. 키의 **복사**는 클립보드 항목을 숨김(Concealed)·임시(Transient)로 표시해 클립보드 관리 앱이 보이거나 남기지 않게 하고, 60초 뒤에도 클립보드에 그 키가 있으면 지운다. 공유 중에는 **원격에서 전체 권한·명령 실행 허용** 스위치가 있다. 꺼져 있으면(기본, 공유를 시작할 때마다 꺼짐) 호스트는 원격 명령 창(kind `shell`)과 전체 권한 실행(Claude bypassPermissions, Codex danger-full-access, Antigravity 전체 권한)을 실행 전에 403으로 거절하고, 클라이언트 창에 이유가 보인다. **공유 중지**는 원격 실행을 멈추고 키를 폐기한다. 앱을 열 때 공유는 항상 꺼져 있다.
- **다른 컴퓨터 연결**: 주소(Tailscale IP, `[IPv6]`, MagicDNS 이름; 포트와 `http://`는 생략 가능)와 키, 이름(비우면 호스트 이름)을 넣고 **연결**. 같은 주소로 새 키를 넣으면 저장된 연결의 키를 바꾼다.
- **연결한 컴퓨터**: 연결마다 상태 점, 주소, 상태 문장, **새로고침**·**연결 해제**·지우기(키도 지운다: Mac은 Keychain, Windows는 아래 절). 연결된 컴퓨터 아래에 공유 워크스페이스와 단추가 있다. **보기**(Mac·Windows): 미러를 시작하고(돌고 있으면 깨우고) 그 워크스페이스를 고른다([원격 미러](#그-컴퓨터의-창-그대로-원격-미러)). 호스트가 미러 목록에 404로 답하면(미러가 없는 이전 버전) 단추가 예전의 **열기**로 돌아온다. **열기**는 그 워크스페이스를 사이드바에 원격 워크스페이스로 넣고 Claude 창 하나를 연다.
- **원격 워크스페이스에서 되는 것과 안 되는 것**: 아래 범위를 화면에서 그대로 말한다.

원격 워크스페이스는 사이드바에서 컴퓨터 아이콘과 호스트 이름, 워크스페이스 머리글의 호스트 배지(연결 여부에 따라 강조색·회색), 아래 상태 막대의 "{호스트}에서 실행 · 연결됨/연결 안 됨"으로 구분한다. 세션 정보에는 **실행 컴퓨터** 줄이, 실행 설정에는 "이 창은 {호스트}에서 그 컴퓨터의 CLI와 계정으로 실행됩니다" 줄이 붙는다. 빈 원격 창은 같은 내용과 쓸 수 없는 기능을 안내한다.

## 실행

- 원격 창의 요청은 호스트의 `ProcessRunner`가 호스트의 CLI·계정·환경으로 실행한다. 모델, 권한 모드(계획 모드와 Claude Auto, Codex 승인 요청 포함), 사고 강도, Fast·웹 검색·네트워크 설정, 재개 ID, 첨부, 설정 → 모델의 페이즈 모델이 그대로 넘어간다. 호스트 CLI가 없거나 지원하지 않는 설정은 클라이언트가 호스트의 `/info` 응답으로 먼저 거르고, 호스트도 실행 전에 다시 확인해 거절한다.
- 호스트가 CLI 출력을 같은 파서(`CLIStreamParser`, Codex 세션 기록과 Antigravity 하위 에이전트 감시 포함)로 읽어 만든 실행 이벤트를 클라이언트가 커서로 받아 자기 창의 이벤트로 적용한다. 그래서 기본 보기와 마이티 보기(흐름·기록·파이프라인)가 로컬 실행과 같은 경로로 그려진다. CLI의 원시 줄 대신 파싱된 이벤트를 보내는 이유는, 파서가 호스트에만 있는 파일(Codex 세션 기록, Antigravity 하위 에이전트 기록, mods 브리지)을 함께 읽기 때문이다.
- 권한·질문·계획 요청은 클라이언트의 같은 카드로 뜨고, 답은 호스트 실행으로 전해진다. 실행 중에 보낸 요청은 클라이언트의 대기열에 들어가 지금 실행이 끝난 뒤 새 실행으로 호스트에 간다. 실행 중인 턴에 덧붙이는 길은 없다.
- 원격 명령 창(kind `shell`, 호스트가 **원격에서 전체 권한·명령 실행 허용**을 켰을 때만)은 명령마다 호스트의 공유 폴더에서 `$SHELL -l -c`를 새로 띄운다(Mac 호스트. Windows 호스트는 아래 절). 대화형 프로그램과 비밀번호 입력은 지원하지 않는다. 로컬 터미널 창(Ghostty PTY)은 원격에 쓰지 않는다.
- 첨부는 내용 자체를 보낸다. 최대 8개, 파일당 5 MiB, 합계 8 MiB.
- 앱을 다시 열면 원격 창과 연결 목록은 남고 연결은 "저장됨" 상태다. 원격 창에서 처음 보내거나 **새로고침**할 때 키를 읽어(Mac은 Keychain, Windows는 아래 절) 다시 연결한다.
- 호스트에서 다른 컴퓨터의 실행이 도는 동안에는 그 컴퓨터의 CLI 업데이트와 플러그인 변경을 미룬다(Windows 호스트도 같다. 아래 절).

원격 워크스페이스에서 쓰지 않는 것과 이유(모두 이 컴퓨터의 디스크·네트워크·프로세스를 읽는다):

| 기능 | 원격에서 |
| --- | --- |
| 마이티 오케스트레이션(위임, 자식 작업 트리) | 끔. 호스트 실행에는 위임 서버를 붙이지 않고, 입력창의 작업 트리 단추도 나오지 않는다 |
| 파일 창 | 만들 수 없음(메뉴에서 빠지고, 단추는 꺼짐). 앱 안 브라우저는 0.5.1에서 없어졌다 |
| 파일을 읽는 스타일(작업 폴더 스타일, 상태 파일, 사전 조건 검사) | 스타일 선택기가 나오지 않음. 원격 창은 자유 요청만 |
| 에이전트 터미널·웹 열기 도구(`run_in_terminal`, `open_url` — 0.5에서는 기본 브라우저로 연다) | 호스트 실행에는 창별 MCP 서버를 붙이지 않음 |
| 상태 줄, git 배지, 작업 폴더의 슬래시 명령, 이전 세션 이어가기, 이전 요청 불러오기 | 쓰지 않음(사용자 수준 슬래시 명령만) |
| 플러그인 관리, CLI 로그인 터미널 | 호스트의 Mighty Code에서 한다 |
| 그림 미리보기 | 호스트의 그림 캐시 키라 클라이언트에서는 뺀다 |

## 연결이 끊길 때

- 실행 중 요청이 실패하면(네트워크, 호스트 종료, 공유 중지) 그 연결의 실행 창은 모두 오류로 끝나고 "원격 연결이 끊겼습니다…" 줄이 남는다. 연결은 "연결 해제"와 이유를 보인다.
- 클라이언트의 폴링이 하트비트다. 호스트는 30초 동안 폴링이 없는 실행을 멈춘다.
- **연결 해제**는 그 연결의 실행을 멈추고 연결을 남긴다. **새로고침**이나 원격 창에서 보내기로 다시 연결한다.

## 그 컴퓨터의 창 그대로 (원격 미러)

연결한 컴퓨터(호스트)가 공유한 워크스페이스를, 호스트에 이미 열려 있는 에이전트 창(대화, 마이티 보기·진행 상황, 상태)과 함께 이 컴퓨터(클라이언트) 사이드바에 그대로 보여 주고, 여기서 계속 쓰게 한다. 창은 호스트의 것이다. 클라이언트에서 보낸 글은 휴대폰에서 보낸 것처럼 그 호스트 창의 다음 요청이 된다(실행 중이면 호스트의 대기열). 2026-11-13 Mac(Swift)과 Windows(C#)에 같은 와이어로 만들었고([Windows 구현](#windows-구현)), 0.5는 Rust로 옮겼다(`native/tauri/crates/mighty-remote/src/remote/mirror/`의 `host.rs`·`client.rs`·`desktop_host.rs`, 호스트 `remote/host/`, 클라이언트 `remote/client/`). 그래서 Mac 클라이언트가 Windows 호스트를, Windows 클라이언트가 Mac 호스트를 비춘다.

### 화면 (클라이언트)

- **사이드바**: 이 컴퓨터의 워크스페이스 아래에 서버마다 머리글 "원격 · {이름}"과 "주소 · 상태"(연결됨·다시 연결하는 중·연결 끊김·연결 전·저장된 연결 없음), 상태 점(초록·주황·회색)이 있고, 그 아래에 그 서버의 워크스페이스가 있다. 저장한 연결은 워크스페이스가 없어도 머리글이 보이고, 검색 중에는 맞는 워크스페이스가 없는 서버가 빠진다. 머리글의 … 메뉴는 **연결**(=새로고침)·**연결 끊기**·**원격 연결 설정…**. 머리글 도움말은 미러가 멈춘 이유나 연결의 상태 문장. 사이드바 머리글의 "워크스페이스 N"은 이 컴퓨터의 것만 센다. 이전 방식의 원격 워크스페이스도 자기 서버 묶음에 들어가고 호스트 이름 줄을 그대로 단다(미러 워크스페이스에는 그 줄이 없다).
- 미러 워크스페이스는 이름 바꾸기·목록에서 빼기가, 미러 창은 이름 바꾸기가 메뉴에 없다(이름은 호스트의 것). 창 닫기는 호스트의 그 창을 닫는다. **창 추가**의 에이전트 창은 호스트의 그 워크스페이스에 새 창을 만들고, 다음 목록에 나타나면 고른다. 명령 창은 만들 수 없다.
- **창 띠**(`MirrorPaneBanner`, 창 머리 아래): "원격 창 · ● {호스트}에서 실행 중 · {상태}", 호스트 창이 창마다 worktree에서 일하면 "브랜치 ← 기준", 호스트 대기열에 요청이 있으면 "대기 중인 요청 N개"(마우스를 올리면 글). 도움말은 무엇이 호스트로 가고 무엇을 쓸 수 없는지와 최근 80개까지 보인다는 것. **상태 막대**는 "원격 · {호스트}에서 실행 중 · {상태}".
- **대기열**(MC-49): 미러 창의 입력창 위 대기열은 호스트 창의 대기열이다. 로컬 창과 같은 목록(번호, 글, **바로 실행**, **고치기**, ↑/↓, ×)으로, 호스트에서 요청이 들어오고(호스트에서 입력하거나 이 컴퓨터·휴대폰에서 실행 중에 보냄), 실행이 앞 요청을 가져가고, 지워지고, 고쳐지고, 순서가 바뀌고, 바로 실행되는 대로 다음 폴링(보고 있으면 1초)에 따라온다. ×, **바로 실행**, **고치기**, ↑/↓는 호스트로 가서 호스트의 규칙대로 되고(휴대폰의 대기열 처리와 같다), 성공하면 다음 폴링 전에 여기 먼저 반영된다. 글이 500자에서 잘려 온 행은 여기서 고칠 수 없다(나머지가 사라지므로). 옮기기는 된다. worktree 행의 바로 실행은 호스트 창의 에이전트로 새 worktree 자식 창을 연다(여기서 에이전트를 고르지 않는다). 다른 에이전트를 골라야 하는 행은 기다린다. 이 대기열 행동을 받지 않는 이전 버전 호스트의 대기열은 단추 없이 보이기만 하고, ×와 바로 실행만 받는 호스트(MC-49 첫 판)에는 고치기와 ↑/↓가 없다. 첨부는 이름 없이 글만 보이고, 앞 16개, 글 500자까지다.
- 미러는 연결이 될 때 저절로 시작한다(설정의 **연결**·**새로고침**, 머리글의 **연결**, 원격 창에서 보내기로 이어진 연결, **보기**). **연결 해제**는 미러를 멈추고 창은 마지막 모습으로 남는다(보내기는 "연결되어 있지 않습니다"로 막는다). 연결을 지우면 그 서버의 미러 워크스페이스와 창이 사라진다. 미러는 저장하지 않으므로 앱을 다시 열면 없다. 연결은 "저장됨"으로 시작하고, 연결하면 다시 나온다.

### 와이어 (프로토콜 2 안의 미러 버전 1)

요청은 모두 기존 `/v2/` 규칙(키, `x-mighty-remote-version: 2`, Tailscale 상대, `Origin` 없음, 초당 횟수, 상대마다 연결 수)을 그대로 거친다. 미러의 답에는 `protocol: 2`와 `mirror: 1`이 있고, 클라이언트는 다른 `mirror` 값을 거절한다. 공유 픽스처는 `native/contracts/fixtures/remote-mirror/`(`endpoints.json`이 경로·본문·답을 묶는다. 기존 `remote-v2/`는 Windows 검사가 파일 목록을 세므로 따로 둔다).

호스트는 **공유 워크스페이스의 이 컴퓨터 에이전트 창(kind `claude`)만** 보인다. 공유하지 않은 워크스페이스의 창은 id를 알아도 404, 명령 창과 이 호스트가 가진 다른 컴퓨터의 창(원격 워크스페이스·미러)은 목록에 없다.

| 경로 | 본문 | 답 |
| --- | --- | --- |

- **요약**(`RemoteMirrorSummary`): `id`, `workspaceId`, `title`(200자까지), `kind`(`claude`), `provider`(알려진 id), `model`(200자까지), `status`(`idle`·`running`·`completed`·`error`·`stopped`, 그 밖의 값은 호스트가 `idle`로 보낸다), `revision`(16진수 64자까지), `pending`(기다리는 도구·질문·계획 요청과 Antigravity 카드), `queued`(대기열 수), `branch?`(창의 worktree 브랜치).
- **상세**(`RemoteMirrorSession`): `id`, `workspaceId`, `title`, `titleMode?`, `kind`, `provider`, `model`, `status`, `createdAt`, `settings`(`RunSettings` 그대로), `agentViewMode?`, `mightyStyle?`, `logs`(최신 80개 = 휴대폰의 `MobileSessionDetail.maximumEntries`, 그림 항목은 `system`으로 바꾸고 그림 참조를 뺀다), `hasOlder`, `graphRuns`(최신 20개 = `MobileWire.mightyRuns`, 하위 에이전트의 `outputFile`과 항목의 그림을 뺀다), `todoProgress?`, `backgroundWork?`, `startedAt?`·`finishedAt?`(ISO 8601, 지금 요청의 시계), `permissions`(기다리는 것만, 최신 32개), `queued`(`[{id, text, runNow?, cut?}]` 앞 16개, 글은 500자까지), `branch?`, `base?`, `queueActions?`, `queueActionNames?`. MC-49에 더한 것: `runNow`는 그 행에서 바로 실행이 할 일(호스트 입력창의 이름 `worktree`·`agentMenu`·`here`·`steer`·`held`·`waitsForTurn`·`waitsForHeld`·`waitsForUpdate`, 단추가 없는 행은 뺀다, 모르는 이름은 단추 없음), `cut: true`는 글이 500자에서 잘렸다는 뜻(클라이언트가 고치지 않는다), `queueActionNames`는 호스트가 받는 대기열 행동(`remove`·`runNow`·`edit`·`move`; 모르는 이름은 버린다), `queueActions: true`는 `remove`와 `runNow`를 받는다는 뜻(MC-49 첫 판 클라이언트가 읽는 것. 첫 판 호스트는 이것만 보내고, 그때 클라이언트는 그 둘만 받는 것으로 읽는다). 받지 않는 호스트는 모두 뺀다. 모두 없어도 되는 덧붙임이라 이전 클라이언트·Mac은 건너뛰고, 이전 호스트의 상세는 그대로 읽힌다.
- **크기**: 상세 JSON은 1.5 MiB(`RemoteProtocol.maximumPollBytes`) 안. 넘으면 오래된 그래프 실행부터 빼고(하나 남김), 다음 오래된 기록부터 빼고(하나 남김, `hasOlder: true`), 그래도 넘으면 글마다 32 KiB로 자르고, 마지막으로 그래프를 비운다(`RemoteMirrorSupport.fitted`).
- **revision**: 창의 revision은 상세가 싣는 것 가운데 바뀔 수 있는 것의 SHA-256 앞 12바이트(16진수 24자). 재료는 상태, 제목, 제공자, 모델, 권한 모드, 사고 강도, 보기 모드, 스타일, 기록 수, 브랜치, 마지막 12개 기록의 `id:글 바이트 수:활동 상태`, 마이티 그래프 digest(휴대폰의 `MobileMightySupport.digest`), 할 일 `id:status`, 백그라운드 작업 `id:status`, 실행 시계, 기다리는 요청 `id:runId:state`, 대기열 id(Rust 호스트는 순서대로 id와 글 전체와 `runNow`: 같은 길이로 고친 글과 순서 바꾸기도 revision을 움직인다). 목록의 revision은 워크스페이스 `id:name`과 창마다 `id:revision:title:status:pending:queued`의 같은 digest. 클라이언트는 같은지만 보므로, 다른 구현은 재료가 달라도 된다. "상세가 바뀌면 반드시 바뀐다"만 지킨다.
- **오류**: 400 잘못된 본문·쿼리·빈 글, 401 키, 403 공유하지 않은 워크스페이스에 새 창·전체 권한 창에 보내기인데 스위치 꺼짐(`remote.host.error.fullAccessOff`)·`always: true`인데 스위치 꺼짐(`remote.host.error.antigravityAlways`), 404 창 없음·공유 밖·미러 없음(앱이 아직 넘겨주지 않았거나 이전 버전 호스트), 409 앱이 거절(메시지가 이유), 415 JSON 아님, 503 공유가 멈추는 중.
- **본문 한도**: `submit`만 첨부 때문에 12 MiB(`AttachmentSupport.maximumRequestBytes`, `RemoteMirrorRoutes.isSubmit`), 나머지는 512 KiB. 글은 400,000바이트까지, NUL 없음, 첨부는 8개까지.

### 호스트 동작

- 읽기는 메인 액터에서 그 순간의 창으로 한다(`RemoteMirrorBridge` → `AppStore.mirrorSummaries`·`mirrorPane`·`mirrorPaneInfo`). 행동은 휴대폰 m1의 처리(`MobileRemoteBridge`)를 그대로 쓴다: 보내기(`mobileSubmit`, 실행 중이면 대기열), 멈추기, 권한·질문·계획 답, 새 창(`mobileCreateSession`: 워크스페이스의 worktree 모드가 묻지 않고 정한다), 닫기. 그래서 휴대폰에서 되는 것과 안 되는 것이 같다.
- 공유 워크스페이스 목록은 요청마다 저장 상태에서 읽고, 창은 앱의 지금 상태에서 읽는다. 창 128개까지.

### 클라이언트 동작

- 미러 워크스페이스는 `remote: {connectionId, workspaceId, hostName, mirror: true}`인 `Workspace`, 미러 창은 `mirror`(`RemoteMirrorReference`: `connectionId`, `hostSessionId`, `hostWorkspaceId`, `hostName`)가 붙은 `RunSession`이다. 둘 다 id는 `mirror-` + SHA-256(UTF-8 `connectionId` + `"\0"` + 호스트 id)의 앞 16바이트(16진수 32자)라서, 같은 연결의 같은 호스트 창은 늘 같은 id다.
- 저장하지 않는다: `StateRepository.save`가 `AppSnapshot.withoutMirrors()`로 미러 워크스페이스·창·그 배치·모드·활성 창·펼침과 활성 워크스페이스·창 id를 빼고 쓴다. `RunSession.mirror`는 Codable 키에도 없다. 창 128개 한도(`ownSessionCount`)는 이 컴퓨터의 창만 센다.
- 원격 워크스페이스이므로 디스크·프로세스를 읽는 기능(위 [실행](#실행)의 표)은 그대로 꺼지고, 휴대폰에도 비추지 않는다. 창 worktree 띠·병합 같은 git 일도 없다(브랜치는 띠에 글로만).
- 보내기·멈추기·권한/질문/계획 답·새 창·닫기는 위 경로로 간다. 보내기는 입력창의 글과 첨부를 비우고 보내며, 호스트가 거절하면 되돌려 놓고 오류를 보인다. 연결이 끊긴 서버의 창은 보내기 전에 막는다.
- **폴링**: 연결마다 작업 하나가 `GET /v2/mirror?since=`를 묻는다. 그 연결의 창이 실행 중이거나 답을 기다리거나, 사용자가 그 연결의 미러 워크스페이스를 보고 있으면 1초, 아니면 5초. 워크스페이스·창 선택, 보내기, 답, 멈추기, 새 창, 닫기가 기다림을 바로 깨운다. 연결이 끊기면 멈춘다. 상세는 보고 있는 워크스페이스의 창과 답을 기다리는 창 가운데 요약의 revision이 마지막으로 읽은 상세의 revision과 다른 것만, 한 번에 16개까지 읽는다.
- 목록을 받으면 미러 워크스페이스·창을 한 번에 만들고 고치고 지운 뒤 배치를 맞춘다. 상세를 받으면 제목·제공자·모델·상태·설정·스타일·기록·그래프·할 일·백그라운드 작업·실행 시계를 덮어쓰고(보기 모드는 호스트가 보냈을 때만), 기다리는 요청을 그 창의 권한 카드로 둔다.
- **실패**: 429·503·시간 초과·연결 끊김은 10초 동안 1초마다 다시 묻고 머리글에 "다시 연결하는 중". 그래도 안 되면 연결을 끊긴 것으로 바꾸고 미러를 멈춘다. 401이면 연결이 끊긴 것으로 바꾼다(키가 바뀜). 호스트가 답은 하는데 거절하면(이전 버전 호스트의 404 등) 연결은 그대로 두고 미러만 멈추고 머리글 도움말에 이유를 둔다. 404면 설정의 단추가 **열기**로 돌아와 그 호스트에는 이전 방식의 원격 창을 계속 쓴다. 상세가 404·409면(목록과 상세 사이에 닫힘) 그 창만 건너뛰고 다음에 목록 전체를 다시 읽는다.

### 지금 안 되는 것

- 명령 창은 비추지 않고 미러 워크스페이스에 만들 수 없다. Antigravity 권한 카드는 `pending`에만 세고 카드로 오지 않는다(호스트나 휴대폰에서 답한다).
- 이름 바꾸기, 모델·권한 모드·사고 강도 바꾸기는 호스트로 가지 않는다(다음 상세가 호스트의 값으로 되돌린다). 대기열 요청은 지우고, 바로 실행하고, 고치고, 순서를 바꿀 수 있다(MC-49). 잘려 온 긴 글은 고치지 못한다. 호스트 창의 delegation 보류 항목은 미러 대기열에 보이지 않는다.
- 기록은 최신 80개까지(`hasOlder`), 이전 기록을 불러오는 길은 없다. 그림은 빠진다.
- 앱을 열 때 저절로 연결하지 않는다(연결은 "저장됨"으로 시작한다).

2026-11-13. 아래 [Windows가 따를 규칙](#windows가-따를-규칙) 1~8을 그대로 따른다. 파일: Core `Remote/RemoteMirror.cs`(와이어·revision·상세 JSON·검사·`WithoutMirrors`), `Remote/RemoteHostService.Mirror.cs`(경로), `Remote/RemoteMirrorDesktopHost.cs`(호스트의 창 읽기와 행동), `Remote/RemoteClientService.Mirror.cs`(요청), `DesktopService.Mirror.cs`(폴링과 상태), 창의 `MainWindow.RemoteMirror.cs`, 웹 셸의 `shell/servers.ts`·`shell/Sidebar.tsx`·`pane/MirrorStrip.tsx`. Mac과 다른 점:

- **호스트**: 읽기와 행동은 `RemoteMirrorDesktopHost`가 창의 스레드에서 한다. 행동은 Windows 휴대폰 라우터(`MobileDesktopRouter`)의 m1 처리를 그대로 부른다(권한·질문·계획 답, 멈추기, 닫기, 새 창). 보내기만 업로드 id 대신 본문의 첨부를 받으므로 `MobileDesktopRouter.SubmitInlineAsync`가 같은 데스크톱 동작과 보내기 자리를 쓴다. 휴대폰 라우터가 없으면(앱이 뜨는 중) 행동은 409 `remote.mirror.error.unavailable`. 보내기의 403은 `RemoteHostService.MirrorRefusal`(`FullAccessRefusal`과 같은 규칙: 전체 권한 창, Windows 호스트의 Claude가 아닌 에이전트 창). 창 revision의 재료에 Mac의 것 말고도 설정 전체, 제목 모드, 기준 브랜치, 백그라운드 작업의 턴 끝, 대기열 글 길이를 넣는다.
- **상세 JSON**: Windows 타입을 Mac의 JSON으로 쓴다(`RemoteMirrorSupport.Write`): `inputJson`→`inputJSON`, 그림·`outputFile` 빼기, 항목·그래프·요청·작업 안의 시각은 `RemoteWireEvents.Normalize`. 세션의 `startedAt`·`finishedAt`·`createdAt`은 Mac의 `ISO8601DateFormatter` 기본형(초 단위)만 읽히므로 초 단위로 쓴다. 읽을 때(`Read`)는 그래프·할 일·백그라운드 작업·항목의 활동이 Windows 타입으로 안 읽히면 그것만 빼고 창은 받는다.
- **클라이언트**: 미러는 `DesktopService`가 들고 있다. 연결의 `Changed`에서 연결됨으로 바뀌면 시작, 끊기면 멈춤, 지워지면 그 미러 워크스페이스·창을 뺀다. 상태 파일에는 `StateStore.SaveAsync`가 `WithoutMirrors()`로 빼고 쓴다. `StateStore.Normalize`는 미러 워크스페이스를 이 PC의 64개와 따로(연결 수 × 64), 미러 창을 128개와 따로(연결 수 × 128) 두고, 미러 창의 글은 이 PC 창의 글 예산을 쓰지 않는다. `PaneLayout.HasRoom`은 이 PC 창만 센다. 미러 창이면 `Launch`·`StopAsync`·`RespondToToolPermission`·`AnswerQuestionnaire`·`AnswerPlan`·`CloseSessionAsync`와 창의 `AddPane`이 호스트로 보낸다. 이름 바꾸기와 목록에서 빼기는 아무것도 하지 않는다. 행동이 호스트에서 거절되면 `MirrorFailed`로 창의 오류 줄에 그 말이 나온다.
- **화면**: 웹 셸이 그린다. 사이드바의 서버 머리글(`ServerHeader`: 점, "원격 · 이름", "주소 · 상태", … 메뉴의 연결·연결 끊기·원격 연결 설정…), 미러 창 띠(`MirrorStrip`), 상태 막대(`status.mirror`), 설정의 **보기**. 미러 워크스페이스·창의 메뉴에는 이름 바꾸기·목록에서 빼기가 없고, 창 추가 메뉴에는 명령 창이 없다. WinUI 자체 화면(웹 셸이 꺼졌을 때)은 상태 막대 글만 미러를 말하고, 사이드바 묶음과 창 띠는 없다.
- **검사**: Core `RemoteMirrorVerification`(픽스처 9개 파일과 목록, 클라이언트 id가 Mac 값과 같음, 한도와 revision, 저장하지 않음과 창 한도, 루프백 호스트 경로와 403·404·409, Windows 클라이언트↔Windows 호스트 전체, 이전 호스트의 404), 웹 `shell/servers.test.ts`·`pane/mirror.test.ts`. Windows 호스트가 쓴 상세를 Mac 클라이언트가 읽는지는 픽스처 왕복으로만 확인했다(Mac 쪽 실기·교차 검사는 아직).

### Windows가 따를 규칙

1. **호스트**: 위 표의 경로·본문·답·상태 코드와 한도(창 128, 기록 80, 그래프 20, 기다리는 요청 32, 대기열 16개·500자, 상세 1.5 MiB, 제목·모델 200자, revision 16진수 64자까지)를 그대로. 공유 워크스페이스의 이 PC 에이전트 창만. `status`는 다섯 단어(그 밖은 `idle`). `since`가 지금 revision이면 `unchanged: true`와 빈 목록. revision은 상세가 바뀌면 반드시 바뀐다.
2. **호스트의 행동**은 Windows 휴대폰 처리와 같은 함수로(보내기·대기열, 멈추기, 답, worktree 모드가 묻지 않는 새 창, 닫기). 전체 권한 창에 보내기와 `always: true`는 스위치가 켜져 있을 때만(같은 403 키). Windows 호스트의 Codex·Antigravity 규칙(`remote.windows.host.error.agentNeedsFullAccess`)도 미러 보내기에 같이 적용한다(같은 이유: 가둘 수 없다).
3. **클라이언트 id**: `mirror-` + hex(SHA-256(UTF-8(`connectionId` + `"\0"` + 호스트 id))의 앞 16바이트), 워크스페이스와 창 모두.
4. **저장하지 않는다**: 상태 파일에 미러 워크스페이스·창·배치·활성 id를 쓰지 않는다. `remote.mirror: true`와 창의 미러 참조는 메모리에만. 창 한도는 이 PC의 창만 센다.
5. **폴링** 1초/5초(위 조건), 선택·행동이 깨운다. 상세는 보이는 워크스페이스의 창과 답을 기다리는 창, revision이 다를 때만, 한 번에 16개.
6. **실패**: 10초 재시도, 401은 끊김, 답한 거절은 연결을 두고 미러만 멈춤, 404면 이전 방식의 **열기**로.
7. **화면**: 서버마다 "원격 · {이름}" 머리글(점, 주소 · 상태 단어, 연결/끊기 메뉴), 미러 창 띠 "원격 창 · {호스트}에서 실행 중 · {상태}"와 대기열 수, 상태 막대 "원격 · …", 설정의 **보기**. 문구는 `remote.mirror.*` 키(로캘에 이미 있다).
8. **픽스처**: Windows Core 검사가 `native/contracts/fixtures/remote-mirror/`를 Mac(`RemoteMirrorWireTests`)처럼 읽는다. 목록·상세는 클라이언트 검사(`RemoteMirrorSupport.valid`와 같은 규칙)를 통과해야 한다.

## 페어링으로 연결 (Tailscale 없이)

Tailscale이 없는 두 컴퓨터도 휴대폰처럼 한 번 페어링하면 원격 미러를 릴레이로 쓴다(Rust 앱; 와이어와 인증은 `docs/relay.md` "다른 컴퓨터"). Tailscale 경로는 그대로다.

- **호스트**: 설정 › 원격 연결 › 이 컴퓨터 공유 › 연결 방식 › 페어링의 "페어링한 컴퓨터의 연결 받기"(`RemoteHost::set_relay`, 메모리에만, 공유를 멈췄다 다시 켜도 유지)를 켜면, 공유하는 동안 릴레이 호스트가 제어 소켓을 연다. 이 스위치가 켜져 있으면 Tailscale 주소가 없어도 공유를 시작할 수 있다(주소 없이, 페어링한 컴퓨터만). "페어링 링크 복사"는 휴대폰 QR과 같은 링크를 비밀 복사(기록 제외, 1분 뒤 지움)하고, "QR 보기"는 그 QR을 그린다. 페어링한 컴퓨터의 요청은 `RemoteHost::serve_relay`가 받는다: 공유 중이고 스위치가 켜져 있어야 하며(아니면 503), Tailscale 피어와 같은 요청 수 제한(기기마다 초당 300, 전체 600)을 거친 뒤 `GET /v2/info`와 미러 라우트만 Tailscale과 같은 코드로 처리한다.
- **클라이언트**: 설정 › 원격 연결 › 다른 컴퓨터 연결에서 "페어링 링크"를 골라 링크를 붙여 넣으면 `RemoteClient::pair`가 새 `clientId`로 페어링하고(호스트 키 확인), 호스트가 준 토큰과 릴레이·`serverId`·공개키를 JSON 하나로 볼트(Mac Keychain, Windows DPAPI)에 연결 키처럼 둔다. 연결 파일(`remote-connections.json`)에는 `relay:`와 `serverId` 앞 16자로 된 주소만 들어간다(이전 앱은 그 항목만 건너뛴다). 다시 연결은 볼트의 토큰으로 한다. 같은 호스트의 링크로 다시 페어링하면 그 연결의 페어링을 바꾼다.
- 연결된 뒤에는 사이드바의 "원격 · 이름", 연결·끊기, 미러 폴링이 Tailscale 연결과 같다(`mirror::client`가 연결마다 HTTP 또는 릴레이 링크로 보낸다). 경로 확인(`ensure_route`)은 하지 않는다.
- **한계**: 프레임 하나가 1 MiB라 보내기 본문(첨부 base64 포함)이 그보다 크면 클라이언트가 "첨부 파일이 페어링 연결로 한 번에 보낼 수 있는 크기를 넘습니다"로 거절하고 아무것도 보내지 않는다. 세션 상세는 호스트가 릴레이용으로 약 960 KiB 안으로 다시 줄인다. 이 컴퓨터의 창을 호스트에서 실행하는 원격 창(`/v2/runs`, 폴 응답이 1.5 MiB까지)은 페어링 연결로 나르지 않는다.

## 프로토콜과 보안 경계

- 앱 사이 프로토콜은 인증된 HTTP/1.1 요청(`/v2/…`, 헤더 `x-mighty-remote-version: 2`)과 실행별 출력 커서다. 지운 기능의 `/v1/`과는 서로 답하지 않는다.
  - `GET /v2/info` — 호스트 이름, 공유 워크스페이스(id·이름·경로), 호스트의 CLI·모델·지원 설정
  - `POST /v2/runs` — 실행 요청(본문에만 프롬프트), `202 {jobId}`
  - `GET /v2/runs/{id}/events?cursor=N` — 커서 뒤의 이벤트, 버퍼에서 빠진 구간이 있으면 `gap`
  - `POST /v2/runs/{id}/stop|steer|permission|questions|plan` — `steer`는 구버전 클라이언트를 위해 라우트만 남았고, 0.4.35부터 호스트는 언제나 `accepted: false`로 답한다. 구버전 클라이언트는 그 답을 받으면 글을 자기 대기열로 넘긴다.
  - Antigravity 권한 카드: 호스트 실행의 이벤트 `antigravityPermission`이 클라이언트 창에 카드를 띄우고, 허용의 이어 보내기는 `POST /v2/runs`에 `antigravityGrant`를 싣는다. 규칙은 그 창을 실행하는 호스트가 자기 agy 설정에 넣고 지운다(자기가 알린 카드의 규칙만, 그 밖은 403). 카드의 규칙은 한 번만 받는다(같은 카드로 다시 보내면 403). 항상 허용(`temporary: false`)은 호스트의 '원격에서 전체 권한·명령 실행 허용'이 켜져 있을 때만 받고(아니면 403 `remote.host.error.antigravityAlways`), 이번만 허용할 수 있는 명령의 항상 허용은 409(`remote.error.antigravityOnceOnly`). 임시 규칙도 그 호스트의 전역 agy 설정에 들어가므로 있는 동안 그 컴퓨터의 모든 Antigravity 실행에 적용된다. 자세한 것은 [mobile-remote.md](mobile-remote.md)의 "Antigravity 권한 카드"
- 무엇이 Tailscale 주소인지는 한 규칙이다(`TailscaleAddresses.select(interfaces:)`): `utun…` 인터페이스 가운데 Tailscale만 쓰는 IPv6 대역 fd7a:115c:a1e0::/48 주소도 가진 것만 Tailscale이고, 그 인터페이스의 두 대역(IPv4 100.64.0.0/10, IPv6 fd7a:115c:a1e0::/48) 주소가 Tailscale 주소다. 통신사 NAT 망은 Wi-Fi·이더넷에도 100.64/10 주소를 주고, Cloudflare WARP 같은 다른 VPN은 자기 utun에 100.96/12 주소를 두기 때문이다.
- 호스트는 그 주소마다 하나씩, 그 주소에만 바인딩하고, 리스너를 그 주소를 가진 utun 인터페이스에 고정한다(시스템이 그 인터페이스를 알려 주지 않으면 Wi-Fi·이더넷·셀룰러·루프백 인터페이스를 막는다). 연결을 받는 순간 상대 주소가 Tailscale 주소가 아니거나 같은 상대의 열린 연결이 이미 8개면 아무것도 읽지 않고 끊는다. 키가 없거나 틀리면 본문을 한 바이트도 읽지 않고 머리만으로 401을 답한다. 요청마다 상대 주소가 Tailscale 주소인지, `Origin` 헤더가 없는지(브라우저 페이지 차단), 키가 맞는지(SHA-256 뒤 상수 시간 비교), 프로토콜 버전이 맞는지, 초당 요청 수를 넘지 않는지 본다. 상대마다 300번, 키가 맞는 요청만 세는 전체 600번이라 키 없는 기기가 진짜 클라이언트를 밀어낼 수 없다. 클라이언트는 실행마다 초당 10번까지만 묻는다.
- Windows 호스트(`RemoteHostService.cs`)는 요청 경로를 쓰인 그대로 읽는다. 퍼센트 인코딩을 풀지 않고 `#` 조각을 떼어 내지 않으므로, Mac 호스트라면 그 경로로 답했을 요청에 404나 400을 답한다. 달라지는 것은 상태 코드뿐이고, 키·Origin·상대 주소 검사를 건너뛰는 길은 없다.
- 호스트가 자기 CLI·플러그인을 업데이트하거나 Claude 모델 목록을 다시 읽는 동안에는 다른 컴퓨터의 새 실행을 503으로 미룬다.
- 클라이언트의 폴링이 잠깐 실패하면(429·503, 시간 초과·연결 끊김) 10초 동안 1초마다 다시 묻고, 그래도 안 되면 연결이 끊긴 것으로 본다.
- 키는 공유를 시작할 때마다 새로 만드는 256비트 난수(base64url 43자)다. 공유를 멈추면 폐기된다. 키는 `Authorization` 헤더로만 다니고 URL·로그·상태 파일에 들어가지 않는다.
- 클라이언트는 주소를 한 번 풀어(`getaddrinfo`) 모든 결과가 Tailscale 주소이고, 그 IP로 가는 경로의 출발 주소가 이 컴퓨터의 Tailscale(터널) 주소일 때만 연결한다(`TailscaleAddresses.sourceAddress`). 이 경로 검사는 연결할 때만이 아니라 요청마다(실행 시작, 폴링, 답·덧붙이기, 중지, 연결된 상태의 `ensureConnected`) 다시 한다. 경로가 터널을 벗어나면 다시 묻지 않고 그 연결을 끊긴 것으로 바꾸고 실행을 오류로 끝낸다. 이 컴퓨터에 Tailscale 주소가 없으면 연결하지 않는다. 호스트가 공유를 다시 시작해 키가 바뀌었으면(401) 연결을 끊긴 것으로 표시한다. 시스템 프록시·쿠키·캐시를 쓰지 않고, 리디렉션은 따르지 않는다(3xx는 오류).
- 실행할 수 있는 작업 폴더는 공유한 워크스페이스 자신의 폴더뿐이다. 클라이언트는 경로를 보내지 않고 호스트의 워크스페이스 id만 보낸다. 호스트는 그 id를 자기 저장 상태에서 찾아 로컬 워크스페이스인지, 폴더가 있는지 확인한다. 공유 목록은 시작 위치를 정할 뿐 파일 접근을 격리하지 않는다. 전체 접근 권한이나 명령 창은 호스트 사용자 권한으로 폴더 밖에도 닿는다.

## 저장

- 워크스페이스의 `remote` 값은 `{"version": 2, "connectionId", "workspaceId", "hostName"}`이다(`RemoteWorkspaceReference`). 경로는 호스트의 경로이고 이 컴퓨터의 폴더로 쓰지 않는다(`StateRepository.resolveLocalWorkspace`·`ProcessRunner`가 거절).
- 2026-09-28 이전에 저장된 `remote`에는 `version`이 없다. 그런 워크스페이스는 지금처럼 불러올 때 창·배치와 함께 버린다(`StateRepository.keepsWorkspace`). 그 뒤 앱이 저장한 로컬 워크스페이스에는 `remote` 키가 없으므로 원격으로 읽힐 일이 없다. 반대로 2026-09-28부터 이 기능 전까지의 앱(0.4.29까지)은 `remote` 값이 있는 워크스페이스를 버리므로, 버전 2 원격 워크스페이스를 로컬 폴더로 착각하지 않는다.
- 연결 목록(id·이름·주소, 키 없음)은 데이터 폴더의 `remote-connections.json`(권한 600, `version: 2`)에 있다. (Mac) 키는 macOS Keychain(서비스 `dev.mightycode.native.remote`, 계정 = 연결 id, 이 기기에서 잠금 해제 후만)에만 있고, 앱 시작 때는 읽지 않는다. Keychain이 거절하면 키는 앱을 끌 때까지만 메모리에 둔다. 앱이 고정된 서명으로 빌드되므로 "항상 허용"은 업데이트 뒤에도 유지된다. Windows의 키 저장은 아래 절의 **저장(Windows)**.

## Windows와 Mac↔Windows

Windows 앱도 같은 `/v2/` 프로토콜로 공유하고 연결한다. 그래서 Mac→Mac, Mac→Windows, Windows→Mac, Windows→Windows가 모두 된다. 두 앱이 같은 요청·응답·이벤트를 쓰는지는 공유 픽스처 `native/contracts/fixtures/remote-v2/`가 묶는다. Mac이 기준이고, Mac(`RemoteWireFixtureTests`)과 Windows Core(`RemoteWireFixtureVerification`)가 같은 파일을 읽는다.

- **화면**: **설정 → 원격 연결** 탭(`MainWindow.RemoteWorkspaces.cs`)이 모바일과 펫 사이에 있다. 공유(주소·연결 키·고르기·포트·전체 권한 스위치), 방화벽 규칙, 다른 컴퓨터 연결, 연결한 컴퓨터와 공유 워크스페이스가 한 상자 안에 구역별 제목으로 나뉜다. 3초마다 상태를 다시 읽고, 공유가 스스로 멈췄으면 탭에 그 사실을 적는다. 사이드바 워크스페이스 머리글의 네트워크 단추와 **창 추가** 메뉴의 **다른 컴퓨터 연결…**도 이 탭을 연다.
- **연결 줄**: 연결한 컴퓨터의 줄은 Mac처럼 이름과 주소만 보인다. 호스트의 OS는 줄이 아니라 원격 워크스페이스(사이드바의 호스트 이름, 머리글의 호스트 배지, 상태 막대 "{호스트} · {OS}에서 실행 · 연결됨/연결 안 됨", 세션 정보의 **실행 컴퓨터**·**실행 컴퓨터 OS**)에 나온다.
- **호스트(Windows)**: `MightyCode.Core/Remote/RemoteHostService.cs`가 Tailscale 주소마다 `RemoteHttpListener`(TcpListener, HTTP/1.1, 연결마다 요청 하나)를 그 주소에만 바인딩한다. 받는 순간 상대를 거르고 상대마다 연결 8개, 키 없는 요청의 본문은 읽지 않음, SHA-256 뒤 상수 시간 비교, 상대마다 초당 300번·키가 맞는 요청 전체 600번은 Mac과 같다. 실행은 호스트의 `RunManager`(그 PC의 CLI·로그인, 창별 MCP·위임·그림 캐시 없음)로 한다. 이 PC에서 다른 컴퓨터의 실행이 도는 동안에는 CLI 업데이트(수동·자동)와 플러그인 변경을 미룬다.
- **요청 경로**: Windows 호스트는 요청 경로를 쓰인 그대로 읽는다. 퍼센트 인코딩을 풀지 않고 `#` 조각을 떼지 않으므로, Mac이라면 열어 줬을 경로에 Windows 호스트는 404나 400을 답한다. 달라지는 것은 상태 코드뿐이며, 키·`Origin`·상대 주소 검사를 건너뛰는 길이 아니다.
- **명령 창**: Windows 호스트에서는 명령마다 시스템 폴더의 `powershell.exe -NoProfile -NonInteractive -Command <글>`을 공유 폴더에서 새로 띄운다(`RemoteCommandShell`, 환경 변수 `NoDefaultCurrentDirectoryInExePath=1`). Mac 호스트는 `$SHELL -l -c`. 창의 빈 화면 안내(`remote.windows.pane.commandNote`)와 상태 막대·세션 정보는 호스트의 OS(`/info`의 `runtime.platform`: `darwin`·`win32`)를 보여 준다.
- **전체 권한 스위치(가둘 수 없는 에이전트)**: Mac 호스트에서 가둬지는 것은 Codex뿐이다(Codex 자신의 Seatbelt 샌드박스, `sandbox_mode`). agy는 샌드박스 인자 없이 실행되고 검토 모드는 CLI 자체 규칙일 뿐이라, Mac 호스트도 스위치가 꺼져 있으면 Antigravity·pi·opencode·Hermes 원격 실행과 미러 창의 보내기·권한 허용·질문 답·계획 결정을 403(`remote.host.error.agentNeedsFullAccess`)으로 거절한다(0.5.3까지는 C#의 "Seatbelt가 Antigravity도 가둔다"는 전제로 Mac에서 허용했다; `RemoteHost::confined_agent`). Windows에서는 Codex의 가둠도 확인할 수 없으므로, Windows 호스트는 **원격에서 전체 권한·명령 실행 허용**이 꺼져 있으면 다른 컴퓨터의 Claude 아닌 모든 에이전트 실행(Codex·Antigravity·pi·opencode·Hermes)을 권한 모드와 상관없이 실행 전에 403(`remote.windows.host.error.agentNeedsFullAccess`: 다른 권한 모드로는 안 되고 스위치를 켜야 한다는 문구)으로 거절한다(0.5 `mighty-remote/src/remote/host/mod.rs` `full_access_refusal`, 0.4 `RemoteHostService.FullAccessRefusal`, 실패 시 닫힘). Claude는 권한 요청으로 묻기 때문에 스위치가 꺼져 있어도 지금처럼 실행된다.
- **이벤트 맞추기**: Windows 실행 이벤트는 Mac 모양으로 바꿔 보낸다. 로그인 만료 사유는 `auth`이고, 권한 요청 입력은 `inputJSON`이며, 시각은 `yyyy-MM-ddTHH:mm:ss.fffZ`로 쓰고, 그림은 뺀다. 그래프는 Mac의 `graph`(ExecutionGraphNode)로 보낸다. Windows 클라이언트가 실행 요청에 `x-mighty-remote-graph: run`을 붙이면 Windows 호스트는 그 실행에 `graph` 대신 Windows의 `graph_run`(MightyGraphRun)을 보내고, Mac 호스트는 이 머리를 무시한다. Windows 클라이언트는 Mac 호스트의 `graph`를 조용히 버리므로, Mac에서 도는 실행의 Windows 마이티 보기는 대화 기록으로 묶은 블록만 보인다.
- **클라이언트(Windows)**: `RemoteClientService`는 요청마다 그 IP로 가는 출발 주소가 이 PC의 Tailscale 주소인지(UDP 소켓 연결, 보내는 것 없음) 다시 본다. 리디렉션을 따르지 않고 프록시·쿠키를 쓰지 않으며, 응답은 2 MiB까지, 15초(첨부 실행 60초) 안에 읽는다. 폴링이 429·503·시간 초과로 실패하면 10초 동안 다시 묻는다. 쓸 수 없는 이벤트 하나는 빼고 안내 줄을 남기며, 기다리는 권한 요청은 창마다 최신 32개만 둔다. 이 PC의 파일·브라우저·터미널·Explorer 열기·스타일·위임은 원격 워크스페이스에서 꺼 두고(워크스페이스의 폴더를 읽는 곳은 모두 `LocalPath`를 거친다), 이 PC의 CLI 업데이트·로그인 대기는 원격 창을 붙잡지 않는다.
- **저장(Windows)**: 연결 목록은 `remote-connections.json`(버전 2, 키 없음, 임시 파일에 쓴 뒤 바꾸는 원자적 쓰기), 키는 `<프로필>\remote-keys\<id의 SHA-256>.bin`에 현재 Windows 사용자 DPAPI(`CryptProtectData`, `ProtectedData`의 CurrentUser와 같음)로 암호화해 둔다. DPAPI가 거절하면 키는 앱을 끌 때까지만 메모리에 있다. 연결 목록 파일을 다른 프로그램이 붙잡고 있어 읽지 못하면 덮어쓰지 않고 잠시 뒤 다시 읽는다. `Workspace.remote`는 Mac과 같은 `{"version": 2, …}`이며 버전이 없거나 다른 값이면 불러올 때 버린다.
- **방화벽**: 휴대폰 직접 연결과 같은 규칙 하나(TCP, 이 앱 실행 파일, 100.64.0.0/10·fd7a:115c:a1e0::/48에서만)가 켜진 포트를 함께 연다. 휴대폰 직접 연결이 켜져 있으면 그 포트, 이 PC가 공유 중이면 공유 포트로, 둘 다 켜져 있으면 두 포트를 한 규칙에 넣는다(`RemoteWorkspaceFeatures.FirewallPorts`). 두 설정 탭(모바일, 원격 연결) 어느 쪽에서든 같은 규칙을 고친다. 원격 연결 탭의 단추는 **방화벽 규칙 추가**·**방화벽 규칙 갱신**(규칙이 있을 때)·**방화벽 규칙 지우기**이고, 모바일 탭은 같은 일을 **규칙 추가**·**규칙 지우기**(와 규칙이 있을 때 **방화벽 규칙 갱신**)로 부른다. 한 번에 하나만 실행한다. 추가·갱신·지우기를 할 때마다 Windows가 관리자 확인 창(UAC)을 한 번 띄운다. 앱은 이 밖에 권한 상승을 요청하지 않는다. 앱이 규칙을 저절로 바꾸지는 않는다: 휴대폰 직접 연결을 끈 채 공유를 이어 가거나 공유를 멈춘 뒤에도 규칙은 이전 포트를 연 채 남을 수 있고, 그때는 **방화벽 규칙 갱신**으로 맞춘다. 두 탭은 규칙의 포트(`netsh … show rule`이 보여 주는 숫자 목록)가 지금 쓰는 포트를 모두 담지 않거나 읽지 못하면 "갱신 필요"라고 적고(`RemoteWorkspaceFeatures.FirewallNeedsUpdate`), 규칙을 지우면 두 포트가 함께 닫힌다고 적는다.
- **키 복사**: 클립보드 기록(Win+V)과 클라우드 클립보드에 남지 않게 복사하고(`ClipboardContentOptions` IsAllowedInHistory·IsRoamable 끔), 클립보드 모니터링 프로그램이 건너뛰게 `ExcludeClipboardContentFromMonitorProcessing` 형식도 붙이고(Mac의 Concealed에 해당; 붙일 수 없으면 이 표시 없이 복사하되 기록·클라우드 제외는 그대로), 60초 뒤에도 그 키가 클립보드에 있으면 지운다. 이 60초 뒤 지우기는 설정 탭을 닫아도 그대로 돈다. 설정 탭은 복사했는지 실패했는지 말하고, 탭을 닫으면 상태를 다시 읽는 타이머를 멈추고 화면에 보이던 키 값과 쥐고 있던 키를 놓는다.
- **기기 확인 남음**: UAC 창과 방화벽 규칙, Mac→Windows와 Windows→Mac 실제 연결은 Windows PC에서 확인해야 한다(실제 기기 연결은 아직 확인하지 못했다. `docs/windows-screen-checklist.md`의 "원격 워크스페이스").

## SSH 머신 (상대 쪽 설치·페어링 없이, MC-33)

상대 컴퓨터에 Mighty Code가 없어도, 사용자의 OpenSSH로 그 컴퓨터의 폴더에서 터미널과 에이전트를 실행한다(0.6.0, 최소 모드: PTY와 파이프만 쓰고 원격에 아무것도 설치하지 않는다). 사용 안내는 도움말 [원격 연결 › SSH 머신](help/content/ko/remote.md#ssh).

- **구현**: 순수 부분은 `native/tauri/crates/mighty-core/src/ssh/`(`target` 이름 검사, `config` ssh_config의 Host 읽기, `command` 원격 명령과 ssh 인자 배열, `failure` stderr 분류, `files` 원격 파일 명령(목록·읽기, MC-40 편집의 열기·확인·원자적 쓰기), `held` 연결이 끊겨도 이어지는 실행의 원격 스크립트(MC-40)), 실행 엔진의 원격 소유자는 `crates/mighty-run/src/ssh.rs`(`SshLaunch`, 포트 전달 `Forwards`)와 `ssh_held.rs`(붙잡아 둔 실행, MC-40), 앱 쪽은 `src-tauri/src/ssh/`(머신 목록·연결 테스트·워크스페이스 열기·사이드바, `files.rs` 파일 창, `forward.rs` 로컬로 연결)와 `src-tauri/src/settings/ssh.rs`(설정 상자). 워크스페이스 모델은 `Workspace.ssh`(`machine`, `dir`, `host`).
- **머신**: 설정 › 원격 연결 › **SSH 머신**에서 `~/.ssh/config`의 Host(와일드카드·`!` 패턴은 빼고, `Include`는 따라가며 `Match` 블록 안은 무시)를 고르거나 `user@host[:port]`를 입력한다. `-`로 시작하는 이름, 공백·따옴표·`%`·셸 문자, `ProxyCommand` 같은 옵션은 받지 않는다. 목록은 `<data>/ssh/machines.json`(0700 폴더의 0600 파일; 이름, 마지막 테스트 결과, tmux 스위치만). 비밀번호·키는 앱에 없다.
- **연결 테스트**: `ssh -o BatchMode=yes -o ConnectTimeout=10 -T -- <host> 'uname -sm; echo "$SHELL"; command -v tmux || echo no-tmux'`, 전체 20초. 공유 연결을 쓰지 않는다(새 로그인을 시험). 연결할 수 없음·로그인 거부·모르는 호스트 키·바뀐 호스트 키를 따로 알린다. `StrictHostKeyChecking`을 바꾸지 않으므로 처음 보는 호스트 키는 사용자가 터미널에서 받아야 한다.
- **워크스페이스**: 원격 폴더(`/`나 `~`로 시작)를 열면 `Workspace.ssh`가 붙은 워크스페이스가 생기고, 그 `path`는 앱의 빈 로컬 폴더(`<data>/ssh/workspaces/<id>`)다. 그래서 로컬 폴더를 읽는 기능(git 배지, 상태 줄, 스타일)은 빈 폴더를 볼 뿐 원격을 건드리지 않는다. 작업 지도와 창 worktree는 MC-47부터 그 머신에서 읽고 쓴다(아래 **창 worktree와 작업 지도**). 사이드바에는 머신마다 "SSH · 이름" 머리글(상태 점, 마지막 테스트 결과, … 메뉴의 연결 테스트·SSH 머신 설정)과 그 워크스페이스(경로 `host:dir`)가 나온다. 폴링은 없다.
- **원격 명령의 모양 (MC-40)**: ssh가 원격 로그인 셸에 넘기는 명령은 늘 `/bin/sh -c '<스크립트>'` 한 단어다(`command::sh`). 그 단어에는 줄바꿈·백슬래시·`!`가 없고 작은따옴표는 `'"'"'`로 쓴다. 그래서 bash·zsh뿐 아니라 fish(작은따옴표 안에서 `\\`·`\'`를 읽는다)·csh/tcsh(작은따옴표 안 줄바꿈을 거부하고 `!`를 기록으로 읽는다)도 같은 단어로 읽는다. 스크립트에 그런 글자가 있으면(대부분 여러 줄이다) 16진수로 보내고, 원격 `/bin/sh`가 `LC_ALL=C awk`로 바이트를 되살려 `eval`한다(`awk`는 POSIX라 macOS·Linux·busybox에 다 있다). 스크립트는 POSIX `sh` 문법이고, 그 안의 경로·인자는 전처럼 POSIX 작은따옴표로 감싼다. 원격 명령을 읽어야 하는 검사용 가짜 ssh는 `command::unwrap_sh`(Rust)나 `tests/common`의 `DECODE_REMOTE`(셸 함수)로 푼다.
- **터미널 창**: 로컬 PTY에서 `ssh -tt … -- <host> /bin/sh -c 'cd <dir> && exec "${SHELL:-/bin/sh}" -l'`(tmux를 켜면 `cd <dir> && exec tmux new-session -A -s mighty-<창 id>`). 프롬프트(비밀번호, 새 호스트 키)는 창 안에서 사용자가 답한다. 키가 있는 `open_keyed`라 백그라운드 데몬(MC-3)이 켜져 있으면 데몬이 ssh를 소유한다.
- **에이전트 창**: 실행 엔진의 `spawn_keyed`가 받는 요청을 `SshLaunch::run_request`가 만든다: `ssh -o BatchMode=yes -T … -- <host> /bin/sh -c '<스크립트>'`. 스크립트는 그 폴더로 가서, 로그인 셸이 POSIX 계열(sh, bash, zsh, dash, ksh, mksh, ash, yash)이면 `exec "$SHELL" -lc 'exec env NO_COLOR=1 … claude …'`(프로필의 환경이 적용된다), 아니면(fish, csh, tcsh, 그 밖) 그 셸에 `PATH`만 물어(`-lc`, csh·tcsh는 `-c`로 `printf "MIGHTYPATH=%s" "$PATH"`) `/bin/sh`가 CLI를 실행한다(그 셸의 다른 환경 변수는 넘어오지 않는다). 셸 명령 창은 사람이 쓴 명령을 그 로그인 셸에 그대로 준다(csh·tcsh는 `-c`, 그 밖은 `-lc`). CLI는 원격 로그인 셸의 `PATH`에서 찾고, 로컬 CLI는 찾지 않는다. 에이전트 실행은 아래 **붙잡아 둔 실행**으로 원격에서 따로 돈다. Claude의 승인 채널(stdio)은 ssh 파이프로 그대로 오간다. 로컬에만 있는 것(Mods 플러그인 폴더와 브리지, 창별 MCP 서버, 첨부 사본)은 넘기지 않는다. 원격으로 가는 환경 변수는 `NO_COLOR`, `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS`, `CLAUDE_CODE_EFFORT_LEVEL`과 (MC-47) 창 worktree의 값(`PORT`, `MIGHTY_PORT`, `MIGHTY_PORT_COUNT`, `MIGHTY_WORKSPACE_FOLDER`, `MIGHTY_WORKTREE`, `MIGHTY_WORKTREE_NAME`, `MIGHTY_ROOT_PATH`, `MIGHTY_WORKTREE_PATH`)뿐이다(값은 명령줄에 들어가므로 비밀은 넘기지 않는다). Claude·Codex·Antigravity·pi만 되고 ACP 에이전트(opencode, Hermes)는 문장과 함께 거절한다. 셸 명령 창(kind `shell`)도 원격 로그인 셸로 실행한다.
- **파일 창**: 목록은 `cd <dir> && LC_ALL=C ls -1Apq ./'<경로>' | head -n 5001`. `..`·절대 경로·제어 문자는 거절하고 경로는 늘 `./'…'`로 넘긴다. 기본 앱으로 열기·Finder에서 보기는 하지 않는다.
- **파일 편집 (MC-40)**: 열기(미리 보기도)는 링크가 아닌 일반 파일만(`[ -h ] || [ ! -f ]`면 끝 코드 4) `ls -ldn`의 앞 10글자(종류와 권한)와 첫 1 MiB+1바이트를 읽는다(`ssh::files::open_command`). 편집기의 `diskHash`는 `ssh-<SHA-256>-<cksum CRC>-<크기>`다(`src-tauri/src/ssh/files.rs`의 `signature`): SHA-256은 여기서 읽은 바이트를, POSIX `cksum`(다항식 0x04C11DB7, 길이 덧붙임, 반전; Rust 구현을 시스템 `cksum`과 맞춰 검사)은 원격이 파일을 다시 보내지 않고 같은지 보게 한다. 디스크 확인(편집기가 2.5초마다)은 `cksum`만 묻고 다르면 다시 읽어 `modified`로 답한다. 공유 연결이면 2초, 없으면(Windows) 15초 안의 같은 질문에는 지난 답을 준다. ssh가 실패하면 `unchanged`로 답해 거짓 충돌을 만들지 않는다. **저장**은 ① 파일을 다시 읽어 그 서명이 편집기가 연 것과 다르면(덮어쓰기를 고르지 않았으면) 충돌로 거절하고, ② 로컬 저장과 같은 `edit::prepare`로 그 파일의 인코딩·BOM·줄 끝(CRLF)을 지킨 바이트를 만들고, ③ 그 바이트를 ssh의 **표준 입력**으로 보낸다(명령줄에 없다). 원격 스크립트(`write_command`)는 `umask 077`에서 같은 폴더에 `.<이름>.<32자 hex>.edit.tmp`를 `set -C`(이미 있으면 실패, 링크를 따라가지 않음)로 만들어 받고, 받은 바이트의 `cksum`이 보낸 것과 다르면 6(덜 옴), 원래 권한 비트를 주고(`chmod`, setuid·setgid·sticky 제외), 대상의 `cksum`이 ①에서 읽은 것과 다르면 7(그사이 바뀜) — 6과 7은 아무것도 쓰지 않는다 — 같으면 `mv -f` 한 번으로 바꾼다. 임시 파일은 어떤 실패에도(`trap … EXIT`, 끊김의 HUP·PIPE 포함) 지운다. 소유자는 저장한 사용자가 되고 하드 링크는 끊긴다(로컬 저장과 같다). 읽기 30초, 쓰기 60초 제한. 7이면 파일을 다시 읽어 충돌로 답하고 편집기는 평소처럼 다시 불러오기·덮어쓰기를 묻는다. mtime은 쓰지 않는다: GNU와 BSD의 `stat` 형식이 다르고, 내용(크기+CRC+SHA-256)이 더 강한 같음이다. 쓰기가 막힌 앱(`host.writes()`가 거짓)은 전처럼 읽기 전용이라 답한다.
- **공유 연결**: Mac은 `-o ControlMaster=auto -o ControlPath=<폴더>/cm-%C -o ControlPersist=10m`으로 한 머신의 창이 연결 하나를 쓴다. 폴더는 0700이고 `<data>/ssh`가 유닉스 소켓 길이(104바이트, ssh가 만들 때 붙이는 17자 포함)를 넘으면 `/tmp/mc-<uid>-ssh`(이 사용자 소유·링크 아님을 확인)를 쓴다. Windows의 OpenSSH는 ControlMaster가 없어 창마다 연결한다. ssh는 `%SystemRoot%\System32\OpenSSH\ssh.exe`(없으면 `PATH`의 `ssh.exe`), Mac은 `/usr/bin/ssh`.
- **끊김**: 모든 연결에 `ServerAliveInterval=15`, `ServerAliveCountMax=3`. 터미널 창의 ssh가 255로 끝나면 "SSH 연결이 끊겼습니다"와 **다시 연결** 단추(다시 시작과 같은 동작)가 나오고 창 위 SSH 띠에 "연결 끊김"이 붙는다. tmux가 있으면(테스트가 찾으면 기본 켜짐, 머신마다 끌 수 있음) 작업은 원격에서 계속되고 다시 연결하면 같은 세션에 붙는다. 에이전트 실행은 아래처럼 끊겨도 이어진다(셸 명령 창의 명령은 전처럼 끊기면 오류로 끝난다).
- **붙잡아 둔 실행 (MC-40)**: 에이전트 창의 실행은 그 ssh의 자식이 아니다. 시작 스크립트(`ssh::held::start_script`)가 `~/.cache/mighty-code/runs/<32자 hex>`(0700, 이미 있으면 거절)에 실행 스크립트(`cmd`, 직접 실행과 같은 것), 붙잡는 스크립트(`hold`), FIFO `in`, 빈 `out`·`err`·`inlog`를 만들고, `setsid`(없으면 `perl`의 `setsid`, 그것도 없으면 `nohup`)로 붙잡는 셸을 세션 밖에서 띄운다. 그 셸은 `sleep`으로 FIFO의 쓰는 쪽을 쥐고(그래서 연결이 끊겨도 CLI는 입력의 끝을 읽지 않는다) CLI를 `< in > out 2> err`로 실행하고, 끝나면 끝 코드를 `status`에 쓴다. 7일 지난 끝난 실행의 폴더는 다음 시작이 지운다. 이 컴퓨터는 **붙기**(`attach_script`, batch-mode ssh, Mac은 공유 연결)로 읽는다: 첫 줄 `mighty-attach <도착한 입력 바이트 수>`, 그다음은 `tail -c +<오프셋+1> -f out`이고, ssh의 표준 입력은 `cat | tee -a inlog > in`으로 FIFO에 간다. 붙기의 입력이 `in.closed` 없이 끝나거나 `tail`이 닫힌 파이프를 만나면 연결이 끊긴 것이고(끝 코드 4, ssh 자체는 255), `mighty-run`의 `ssh_held`가 2·5·15·30·60·120초, 그 뒤 120초마다 다시 붙는다. 다시 붙을 때는 읽은 바이트 수부터 읽고, 도착하지 않은 입력(`inlog` 크기 뒤)만 다시 보낸다(보낸 입력은 8 MiB까지 기억). 실행 엔진은 끊김을 모른다: 기다리던 승인·질문 카드는 그대로 있고, 끊긴 사이 한 답은 다시 붙은 뒤 CLI에 닿는다. 엔진이 입력을 닫으면, 모든 입력이 간 뒤에 원격에 `in.closed`를 표시하고 FIFO를 쥔 `sleep`을 끝내고 붙기의 입력을 닫는다. CLI가 끝나면 붙기가 0으로 끝나고 `drain_script`가 남은 출력, 끝 코드, 표준 오류의 마지막 64 KiB를 읽은 뒤 폴더를 지운다. 멈추기는 원격에서 `TERM`, 5초 뒤 `KILL`, 끝 코드를 대신 쓴다. 30분 동안 다시 붙지 못하면 여기서는 `ssh.held.error.lost`로 끝난다(원격의 CLI는 끝날 때까지 돈다). 원격이 붙잡기를 못 하면(폴더나 FIFO를 못 만들거나 붙잡는 셸이 안 뜨면) 전처럼 직접 실행한다. tmux는 쓰지 않는다(없는 머신이 많고, 한 방식으로 충분하다). 붙기는 실행의 키로 `spawn_keyed`하므로 백그라운드 데몬(MC-3)이 켜져 있으면 데몬이 붙기의 ssh를 가진다: 앱이 작업을 남기고 끝나면 놓기(`let_go`, `leave`, MC-38의 keptState)는 그 붙기의 것이고, 다음 앱은 그 붙기로 실행을 이어 받는다.
- **요청 변경 검토 (MC-40)**: SSH 창의 요청(그래프 실행)은 원격 스냅숏으로 검토한다(`ssh::review`, mighty-files `remote_review`). 붙잡아 둔 실행의 시작 스크립트가 CLI를 띄우기 **전에** 그 폴더의 `start` 트리를, 붙잡는 셸이 CLI가 끝난 **뒤에** `end` 트리를 만든다. 저장소는 `~/.cache/mighty-code/snapshots/<폴더 실경로의 cksum>`(0700)이고 `runs/<창>/<요청>`에 `<start> [<end>]`, `runs/<창>/order`에 순서를 둔다. 그 폴더가 git 저장소 안이면 MC-18처럼 저장소를 쓰지 않는다: 개인 인덱스(`GIT_INDEX_FILE`, 처음엔 저장소 인덱스의 사본)와 저장소의 객체를 대체 객체로 둔 자기 객체 폴더(`GIT_OBJECT_DIRECTORY`·`GIT_ALTERNATE_OBJECT_DIRECTORIES`)로 `git add -A -- .`·`git write-tree`; 저장소 밖이면 저장소의 bare git 폴더에 그 폴더를 작업 트리로(파일 20,000개 넘으면 스냅숏 없음). git은 `core.fsmonitor=false`, `core.hooksPath=/dev/null`, 자동 정리 없음, `protocol.allow=never`, `GIT_NO_LAZY_FETCH`, 글자 그대로의 pathspec으로 돌아 저장소 설정이 프로그램을 띄우지 못한다. 검토는 ssh 두 번에 읽는다: 그 창의 최근 요청 20개와 각자 바뀐 파일(`git diff-tree -z`, 아직 도는 요청은 지금 폴더와 비교), 그다음 필요한 내용(요청 시작 트리의 원본, 지금 파일과 권한, 같은 파일을 바꾼 뒤 요청의 시작 트리). 규칙은 로컬과 같은 코드다: mighty-files `revert`에 `ReviewOriginals`(원본 보관)·`ReviewFiles`(파일 읽기·쓰기·휴지통) 추상화를 두고, 로컬은 `LocalOriginals`·`FolderFiles`(기존 동작 그대로, 기존 검사 전부 통과), SSH는 `RemoteReview`가 같은 `plan_on`·`apply_on`·`hunk_review_on`·`discard_hunk_on`·`accept_hunks_on`을 탄다. 그래서 거절(`missing`, `unreadable`, `unchanged`, `laterRun`, `conflict`)과 hunk·지문이 같다. 되쓰기는 위 **파일 편집**의 원자적 쓰기로, 읽은 뒤 그 파일의 `cksum`이 바뀌었으면 쓰지 않고 `conflict`다(인코딩·BOM·권한 유지). 요청이 만든 파일은 저장소의 `trash/<32자 hex>/`로 옮긴다(지우지 않는다; 그사이 바뀌었으면 옮기지 않는다). 받기·버리기 기록은 이 컴퓨터의 `hunk-reviews`에 머신·폴더·창·요청 이름으로 둔다(30일). 요청 변경 검토 화면과 검토 대기열(`review.rs`) 모두 같은 길을 쓴다. 로컬 원본 보관소와 달리 에이전트 종류와 상관없다(Codex·Antigravity·pi 요청도 검토된다).
- **첨부 (MC-40)**: 끌어 놓은 파일은 실행 전에 파일마다 ssh의 표준 입력으로 `~/.cache/mighty-code/attachments/<32자 hex>/<순번>-<hex><확장자>`(폴더 0700, `set -C`로 새로 만듦, 받은 `cksum`이 다르면 지우고 6)에 올린다. 그 실제 경로로 로컬 실행과 같은 프롬프트·인자를 만든다(Claude의 그림·PDF는 첫 메시지에 그대로 넣고 다른 파일은 경로와 `--add-dir <폴더>`, Codex는 `--image`, Antigravity는 `--add-dir`, pi는 경로). 붙잡아 둔 실행은 CLI가 끝나면 그 폴더를 지우고, 직접 실행으로 물러난 경우 등 남은 폴더는 다음 업로드가 7일 뒤 지운다. 이 컴퓨터에는 사본을 만들지 않는다.
- **로컬로 연결**: 창의 출력(터미널 출력, 에이전트의 최근 기록)에 `localhost:3000`, `127.0.0.1:5173`, `0.0.0.0:8000`, `[::1]:8080` 같은 주소가 나오면(1024 이상, 최근 4개) 창 위 SSH 띠에 **로컬로 연결 :포트**가 생긴다. 누르면 MC-25 포트 블록과 쓰는 중인 포트를 피한 로컬 포트로 `ssh -N -T -o ExitOnForwardFailure=yes -L 127.0.0.1:<로컬>:localhost:<원격>`을 띄운다. 띠의 `:원격 → localhost:로컬`은 브라우저로 열고 ×는 끊는다. 끊을 때는 그 ssh를 끝내고, 공유 연결이면 `-O cancel -L …`로 마스터에서도 거둔다. 창을 닫거나 머신을 지우거나 앱을 끝내면 모두 거둔다.
- **휴대폰**: SSH 워크스페이스의 창은 이 컴퓨터의 다른 창처럼 휴대폰 목록에 나온다(따로 한 일 없음).
- **보안**: 로컬에서는 늘 인자 배열로 ssh를 띄우고(셸 문자열 없음), 모든 배열은 `-- <검증한 대상>`으로 끝난다. 원격 명령은 `/bin/sh -c` 한 단어이고, 그 스크립트 안의 경로·프로그램·인자는 POSIX 작은따옴표로 감싼다(`~`는 따옴표 밖). 파일 내용과 실행의 입력은 표준 입력으로만 가고, 원격 실행 폴더는 0700(`umask 077`)이며 실행 id는 이 컴퓨터가 고른 32자 hex만 받는다. 명령줄은 로그에 남기지 않는다.

### 창 worktree와 작업 지도 (MC-47)

SSH 워크스페이스의 에이전트 창도 로컬 창과 같은 규칙으로 자기 worktree에서 일하고(도움말 [창마다 worktree](help/content/ko/delegation.md#pane-worktree)), 작업 지도를 연다. worktree와 저장소는 그 머신에 있고, 이 컴퓨터는 worktree의 상태를 복사하거나 캐시하지 않는다.

- **구조**: mighty-delegation `machine`의 `Machine` 트레이트(`git::GitRunner` + 경로 규칙 + 파일 시스템 질문·삭제·복사·공유)를 `pane_worktree`의 모든 단계가 쓴다. 로컬은 `Local`(앱의 git 실행기 `Git`과 `DelegationPaths`, 지금까지의 `std::fs` 호출을 그대로 옮긴 것), SSH는 `Remote`(git은 mighty-run `ssh_git::SshFolder::git`, 파일 시스템은 mighty-core `ssh::worktree`의 스크립트)다. `merge`, `commit_all`, `undo_merge`, `status`, `diff_stat`, `changed_files`, `file_diff`, `has_unmerged_work`, `kept_on_close`, `in_own_place`, `discard`(`cleanup::remove_own_worktree_on`), `worktrees`(목록)와 만들기(`Worktrees::check`·`make_pane`, `worktree::check_with`)는 한 벌의 코드이고 기계만 다르다. 위임 자식의 코드(`Maker::check`, `remove_own_worktree`)는 같은 함수를 `Local`로 부른다. 앱 쪽은 `pane_worktree::Place`(`place_for`, `place_of`)가 워크스페이스마다 기계와 루트를 정한다: 로컬은 `~/.mightycode/worktrees`, SSH는 그 머신의 `<pwd -P 한 홈>/.mightycode/worktrees`(홈과 git 유무만 머신마다 한 번 묻고 기억한다; `src-tauri/src/ssh/worktrees.rs`).
- **원격 git**: git 하나가 ssh 한 번(공유 연결)이고 그 폴더에서 `git -c core.fsmonitor=false -c core.hooksPath=/dev/null -c gc.auto=0 -c maintenance.auto=false -c log.showSignature=false -c gpg.program=/dev/null -c gpg.ssh.program=/dev/null -c gpg.x509.program=/dev/null -c protocol.allow=never …`, 물려받은 `GIT_*`를 모두 지우고 `GIT_OPTIONAL_LOCKS=0 GIT_TERMINAL_PROMPT=0 LC_ALL=C NO_COLOR=1 GIT_NO_LAZY_FETCH=1`(`ssh::worktree::git_script`). 로컬 실행기와 같은 설정이다. 훅은 로컬처럼 앱이 돌리는 모든 git에서 꺼져 있다(로컬도 `core.hooksPath`가 빈 폴더이고 앱의 커밋은 `--no-verify`). 전송은 막고, pull request의 `push`만 `protocol.allow`와 `GIT_NO_LAZY_FETCH` 없이 돈다(그 머신의 자격 증명). 경로를 받는 명령은 로컬처럼 `--literal-pathspecs`를 붙인다(전역 `GIT_LITERAL_PATHSPECS`는 `check-ignore`를 깨므로 쓰지 않는다). 그 머신에서도 시간 제한이 있다(감시 셸이 `KILL`, 끝 코드 252 → `TimedOut`); 이 컴퓨터는 그 시간 + 20초(연결)를 기다린다. 출력은 로컬처럼 1 MiB까지. 폴더가 없으면 250, git이 없으면 251, ssh 실패 255 → `NotStarted`(로컬의 "git을 띄우지 못함"과 같은 답).
- **원격 파일 시스템**(`ssh::worktree`): 경로는 늘 POSIX(`posix::standardized` 등, Windows 앱에서도 바꾸지 않는다). `probe_script`(링크·폴더·있음·크기, 200개씩), `read_inside_script`(worktree 안의 일반 파일, 링크를 거쳐 밖으로 나가지 않음, 1,000,000바이트), `clear_links_script`(안의 디렉터리 링크를 그 자체로 지우고, 그 뒤에도 남으면 1), `unlink_script`, `remove_script`(링크는 그 자체, 폴더에 `u+w` 뒤 `rm -rf`), `mkdir_script`, `free_script`(`df -Pk`, 10 GB 검사), `copy_script`·`share_script`(로컬 `copy`·`copy_mapped_rules`·`share_directories`와 같은 거절 `missing`·`link`·`outside`·`exists`·`limit`·`failed`·`notDirectory`·`notIgnored`, 50 MB·2,000개, 새 파일은 `set -C`, 가는 길의 폴더가 링크면 쓰지 않음; 규칙 정리는 Rust의 `plan_rules`·`plan_shares`를 로컬과 같이 쓴다), `admin_script`·`exclude_script`(공유 폴더의 `info/exclude` 항목을 만든 worktree의 표시 줄로 찾아 지움), `config_script`(`.mighty.yaml`·`.mighty.local.yaml`: 링크·일반 파일 아님·256 KiB 초과는 로컬과 같은 문장으로 거절; `mighty_yaml::load_from_bytes`), `listening_script`(Linux `/proc/net/tcp`·`tcp6`, 그 밖 `netstat -an`), `command_script`(준비·정리 명령: 로컬처럼 `/bin/sh -c`, 여러 줄이면 `-ec`, 로그인 셸의 `PATH`, 그 worktree에서, 표준 입력 닫음), `current_script`(지금 파일, 스냅숏 저장소 없이).
- **잃지 않는 판단**: 원격 질문이 답을 못 하면(ssh 실패) `Err`이고 결코 "없음"이 아니다. `has_unmerged_work`는 `None`(일로 친다)이라 닫을 때 worktree를 남기고, `merge`·`commit_all`은 `gitUnfinished`, `in_own_place`는 거짓(쓰지 않음), `discard`는 멈춘다. 상태·병합·되돌리기·버리기·남기기 판단은 매번 그 머신의 git과 파일을 다시 읽는다(머신마다 기억하는 것은 홈 경로뿐).
- **만들기**: `place.worktrees.check(<원격 폴더>)`(git으로 저장소·브랜치·커밋, 그 머신의 여유 공간) 다음 `git worktree add -b mighty/<id> <루트>/<id> <기준 커밋>`. 쓰기 정책(`may_change_machine`)이 있어야 하고 스모크에서는 원격을 건드리지 않는다. PORT는 열린 창들의 PORT와 그 머신에서 듣는 포트를 피하고, MC-25 포트 블록은 `ports.json`에 `ssh://<머신 id><경로>` 키로 그 머신에서 듣는 포트를 피해 받는다(시작할 때의 정리는 이 키를 지우지 않고, worktree를 지울 때 돌려준다). 복사(`worktree_copy_paths`, `.mighty.yaml` `worktree.copy`), 공유 폴더(`worktree.share`), 준비 명령(승인한 `worktree.setup`과 워크스페이스 준비 명령, `worktree.env`와 worktree 값, 30분)은 그 머신에서 돈다. `.mighty.yaml`은 그 머신에서 읽고 승인은 이 워크스페이스의 키로 이 컴퓨터에 둔다(`repo_tasks::load_worktree_config`·`approve_worktree_config`; 작업 창의 태스크는 여전히 SSH에서 돌지 않는다).
- **실행**: 창의 `working_folder`가 그 머신의 worktree 경로이고, 실행 엔진이 `SshLaunch.dir`을 그것으로 바꾼다(`manager.rs`; 로컬 `is_dir` 검사는 SSH에 쓰지 않고 원격 `cd`가 거절한다). 붙잡아 둔 실행·요청 스냅숏·요청 변경 검토(MC-40)도 그 worktree 폴더 기준이다(`ssh/review.rs`). "이 worktree에서 터미널"은 그 머신의 그 폴더에서 연다(`terminal.rs`).
- **막대**: 상태(20초마다 ssh 4번 안팎), 병합·커밋하고 병합·되돌리기·버리기(자식이 있으면 막음, 확인 뒤)·PR(push는 그 머신에서, 비교 페이지는 이 컴퓨터 브라우저)·변경 보기(파일 diff)·바뀐 부분별 받기·버리기(MC-30: 기준은 그 머신의 `git cat-file blob <공유 커밋>:./<경로>`, 지금 파일은 그 머신에서 읽고, 되쓰기는 MC-40의 원자적 쓰기, 새 파일은 스냅숏 저장소의 trash로; mighty-files `remote_review::RemoteFolder`가 같은 `revert::discard_on`을 탄다)·localhost 열기(그 포트를 MC-33 로컬로 연결로 이어 준 뒤 연다). 파일 관리자에서 보기·편집기에서 열기는 거절하고 막대 메뉴에서 뺀다(`remote: true`). 닫을 때 남기기와 워크트리 목록(다시 열기·병합·지우기)도 같다. 정리 명령(`worktree.teardown`)은 지우기 전에 그 머신에서 돈다.
- **머지 전 점검 (MC-27)**: git 부분(미커밋·충돌·앞섬·뒤처짐)은 그 머신의 git으로 읽는다. pull request·CI·리뷰 스레드는 이 컴퓨터의 `gh`/`glab`이 그 폴더를 모르므로 읽지 않고 `ssh` 사유로 "확인할 수 없음"이다.
- **비교 실행 (MC-29)·창 갈라내기 (MC-28)**: 비교 실행의 자식 worktree는 위임의 로컬 worktree이고, 갈라내기는 대화 기록과 미커밋 파일을 이 컴퓨터에서 옮기므로, SSH 창에서는 문장(`compare.reason.ssh`, `fork.error.ssh`)과 함께 거절한다.
- **작업 지도**: `WorkMapService`가 SSH 워크스페이스의 저장소를 `RemoteRepository`(그 폴더, `GitKind::WorkMap`: 로컬 작업 지도 설정 그대로, 전송 없음)로 읽는다: `rev-parse`, `for-each-ref refs/tags`, 버전마다 `log`(1 MiB, 버전당 커밋 제한 그대로), `VERSION`·`release/<버전>/state.json`·릴리스 노트(`read_first_script`: 링크 아님, 폴더 밖 아님, 앞부분만). 모델은 로컬과 같은 `build_on`이다. 머신에 닿지 못하면 `sshUnreachable`. **요약은 이 컴퓨터의 Claude로 돈다**: 로컬 작업 지도도 빈 임시 폴더에서 프롬프트 글(커밋 제목·요청 글·릴리스 노트)만 받아 요약하므로, SSH도 그 글만 보낸다. 원격 CLI로 돌리면 그 머신의 Claude 설치·로그인이 필요하고 저장소에 닿는 도구를 가진 실행이 되지만, 이 방식에서는 git 기록의 글 말고는 아무것도 나가지 않는다. 요약은 이 컴퓨터의 `work-map` 저장소에 워크스페이스(대역 폴더) 키로 둔다. 사이드바 머리글의 작업 지도 단추와 SSH 워크스페이스 메뉴의 작업 지도가 켜진다.

### Mighty Code 서버 (원격 Mac, MC-33)

SSH 머신이 Mac이면 그 Mac에 Mighty Code를 설치해 창 없이(MC-3 `--server`) 돌려 두고, 이 컴퓨터가 SSH 포트 전달로 그 앱의 원격 미러에 붙는다. 그 Mac의 워크스페이스와 에이전트 창이 [원격 미러](#그-컴퓨터의-창-그대로-원격-미러)로 "원격 · 이름" 아래에 나온다. Tailscale도 페어링 링크도 쓰지 않는다. 사용 안내는 도움말 [원격 연결 › SSH 머신](help/content/ko/remote.md#ssh)의 "Mighty Code 서버".

- **대상**: 원격 **Mac만**(`uname -s`가 `Darwin`, `arm64`·`x86_64`). Linux 빌드가 없고 Windows 원격 설치는 범위 밖이라, 그런 머신의 상자는 이유를 말하고 설치 없는 최소 모드만 쓴다.
- **구현**: 원격 스크립트와 그 출력 읽기는 `crates/mighty-core/src/ssh/server.rs`, ssh로 실행하는 단계는 `crates/mighty-run/src/ssh_server.rs`(`RemoteServer`: `detect`, `install`, `start`, `stop`, `pair`, `remove`), 앱 쪽은 `src-tauri/src/ssh/server.rs`(상태·확인 창·패키지·연결·다시 연결)와 `settings/ssh.rs`의 머신별 "Mighty Code 서버" 줄. 원격 앱 쪽은 `mighty-remote`의 `RemoteHost::new_ssh_tunnel`(루프백 터널)과 `remote::ssh_tunnel`(클라이언트 연결), 제어 API `server.sshPair`와 CLI `mighty server ssh-pair`.
- **원격 명령**: 모든 단계는 그 머신의 `SshLaunch::exec_request`(`-o BatchMode=yes -o ConnectTimeout=10 -T`, Mac은 ControlMaster 공유 연결, 끝은 `-- <검증한 대상>`)로 `/bin/sh -c '<스크립트>'` 한 단어를 보낸다. 로그인 셸이 fish·csh여도 한 단어만 읽으면 된다(MC-40 전에는 여러 줄 스크립트를 그대로 작은따옴표에 넣어 csh·tcsh가 "Unmatched '"로 거부했다. 지금은 위 **원격 명령의 모양**대로 보낸다). 스크립트는 첫 줄에서 `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `umask 077`을 정한다(사용자의 PATH에서 도구를 고르지 않는다). 경로는 `"$HOME"/'…'`처럼 홈만 따옴표 밖에 둔다. 단계마다 시간 제한이 있다(확인 30초, 보내기 30분, 풀기·검증 5분, 멈추기·시작 90초, 바꾸기 60초, 페어링 30초). ssh 자체의 실패(끝 코드 255)는 연결 테스트와 같은 문장(연결할 수 없음, 로그인 거부, 호스트 키)으로, 스크립트의 거절은 그 끝 코드로 구분한다. `sudo`는 어디에도 없다.
- **확인**: `uname -s`, `uname -m`, `sw_vers -productVersion`, `/dev/console`의 소유자와 `id -un`(그 Mac의 화면에 같은 사용자가 로그인해 있는지), `~/Applications/MightyCode.app`(없으면 `/Applications/MightyCode.app`)의 `CFBundleShortVersionString`(`defaults read`)과 그 앱 CLI의 `mighty server status`. 출력은 `이름=값` 줄과 `status-begin`/`status-end` 사이의 JSON이고 마지막 줄 `done=1`이 없으면 답으로 치지 않는다.
- **패키지**: 이 앱의 서명된 업데이트 매니페스트를 앱 업데이트와 같은 서비스(`Service::check`, 빌드의 공개 키로 Ed25519 확인; 사용자가 바꾼 매니페스트 주소도 같은 규칙)로 읽고 `macos` 패키지를 고른다. 매니페스트에는 최신 버전 하나만 있으므로, 그 버전이 이 앱 버전과 다르면 최신 버전을 설치하고 확인 창에서 그렇다고 말한다. `minimumSystemVersion`보다 낮은 macOS는 거절한다. 내려받기는 `<data>/ssh/server/updates/<버전>/MightyCode-macos.zip`에 크기와 SHA-256을 맞춰 본다(앱 자신의 `updates` 폴더와 따로). 서명 키가 없는 빌드(개발 빌드)는 아무것도 설치하지 않는다.
- **설치 단계**(확인 창 뒤): ① **보내기** — `~/Applications/.mighty-install-<32자 hex>`를 새로 만들고(이미 있으면 거절) 패키지를 ssh의 표준 입력으로 `cat`해 받은 뒤 그 Mac의 `shasum -a 256`을 매니페스트 값과 비교한다(진행률은 보낸 바이트로). ② **풀기·검증** — `ditto -x -k`, `.app`이 정확히 하나(링크 아님)인지, 우리가 푼 그 앱에서만 `xattr -dr com.apple.quarantine`, `CFBundleIdentifier`가 `dev.mightycode.native`이고 버전이 매니페스트와 같은지, `codesign --verify --deep --strict -R '=identifier "dev.mightycode.native" and anchor apple generic and certificate leaf[subject.OU] = "<이 앱의 팀>"'`(이 앱이 팀 서명이 아니면 식별자만). ③ **멈추기** — 서버가 돌고 있으면 설치된 앱의 CLI `mighty server stop`(그 pid가 끝날 때까지 기다린다). 검증이 통과하기 전에는 아무것도 멈추지 않는다. ④ **바꾸기** — 같은 폴더 안의 이름 바꾸기 두 번(`~/Applications/MightyCode.app` → 설치 폴더의 `previous.app`, 새 앱 → 제자리). 두 번째가 실패하면 이전 앱을 되돌려 놓는다. 성공하면 설치 폴더(이전 앱, 패키지)를 지운다. 어느 단계든 실패하면 설치 폴더를 지운다. ⑤ **시작** — `~/Applications/MightyCode.app/Contents/MacOS/MightyCode --cli server start`: 앱을 새 세션(setsid, 표준 입출력은 `/dev/null`)으로 `--server` 시작하고 제어 API가 답할 때까지 60초 기다린다. ssh 세션이 끝나도 서버는 남는다.
- **로그인 세션**: AppKit 앱이라 그 Mac의 화면(WindowServer)에 같은 사용자가 로그인해 있어야 시작된다. 확인에서 `/dev/console`의 소유자가 다르면(로그인 창이면 `root`) 미리 알리고, 시작이 실패하면 "그 Mac에 이 사용자로 로그인해 두세요(자동 로그인 권장)"라고 말한다.
- **연결**: ① 그 Mac의 앱 CLI `mighty server ssh-pair`(제어 API `server.sshPair`)가 그 앱의 **SSH 터널 호스트**를 시작하고(이미 돌고 있으면 그대로) 일회용 코드를 낸다: `{port, code, version}`. 코드는 ssh의 표준 출력으로만 오고, 명령줄·로그·화면 어디에도 나오지 않는다. ② 이 컴퓨터는 MC-25 포트 블록과 쓰는 중인 포트를 피한 로컬 포트로 `ssh -N -T -o ExitOnForwardFailure=yes -L 127.0.0.1:<로컬>:localhost:<port>`를 띄우고(로컬로 연결과 같은 `Forwards`, 이름 `server:<머신 id>`) 그 포트가 받을 때까지(10초) 기다린다. ③ 원격 클라이언트 `RemoteClient::connect_ssh`가 그 포트로 `POST /v2/ssh/pair`(코드를 `Authorization: Bearer`로)를 보내 공유 키를 받고, 그 키로 `/v2/info`를 읽어 연결을 `ssh:<머신 id>` 주소로 저장한다. 키는 볼트와 연결 파일에 넣지 않고 메모리에만 둔다(다시 연결할 때마다 새로 페어링한다). 연결이 서면 미러가 평소처럼 시작된다.
- **SSH 터널 호스트**(`RemoteHost::new_ssh_tunnel`, 원격 앱 안): Tailscale 공유와 따로 도는 두 번째 호스트. `127.0.0.1`에만, 시스템이 고른 포트에 바인딩하고 루프백 상대(127.0.0.0/8, `::1`, IPv4-mapped 루프백)만 받는다. LAN·Tailscale 포트를 열지 않는다. SSH로 들어온 사람은 그 Mac의 같은 사용자라 이미 모든 것에 닿으므로, 이 호스트는 로컬 워크스페이스(원격·SSH 워크스페이스 제외)를 모두 공유하고 전체 권한을 켠다. 키 없이 받는 경로는 `POST /v2/ssh/pair` 하나다: 공유 중, `Origin` 없음, 루프백 상대, 상대별 요청 수 제한, 그다음 코드(SHA-256 뒤 상수 시간 비교), 프로토콜 버전. 코드는 1분 동안 하나만 있고(새 코드가 이전 코드를 바꾼다) 맞는 시도에 한 번 쓰인다. 틀린 시도는 코드를 없애지 않는다: 256비트 난수라 맞힐 수 없고, 다른 로컬 사용자가 틀린 코드로 주인의 코드를 없애지 못하게 한다. 다른 경로는 Tailscale 공유와 같은 키 검사를 거친다. 다른 로컬 사용자도 그 포트에 닿을 수는 있지만 키나 코드는 제어 API(0600 토큰)를 거쳐야만 얻는다. 미러 호스트는 공유 호스트와 같은 창을 넘긴다. 이 호스트로 들어온 실행 수는 따로 세어 CLI 업데이트 대기에 더한다. 공유 메모리 동기화(`/v2/memory`, MC-13)도 이 호스트에 붙는다(MC-40): Tailscale 공유와 같은 `MemoryHost`와 원격 실행의 메모리 주입을 쓰고, 다른 경로와 같은 키 검사를 거친다(키 없음·틀린 키·페어링 코드는 401). 범위는 이 호스트가 공유하는 것(로컬 워크스페이스 전부, 원격·SSH 워크스페이스 제외)이고, SSH 사용자는 그 Mac의 같은 사용자라 이미 읽고 쓸 수 있는 것 이상은 열지 않는다. 사용자 메모리는 그 Mac의 공유 설정을 따른다.
- **다시 연결**: 서버 전달의 ssh가 스스로 끝나면(네트워크 끊김, 마스터 종료) 2·5·15·30·60·120초 뒤에 차례로 다시 잇는다(전달을 다시 열고, 새 코드로 페어링하고, 미러 연결). 머신이나 연결이 지워졌거나, 사람이 **연결 끊기**를 눌렀거나, 이미 붙어 있으면 멈춘다. 원격 서버는 그동안 계속 돈다. 사이드바의 연결도 같은 길(`refresh` → 전달·페어링)을 탄다. 원격 서버만 다시 시작돼(포트가 바뀌었거나 키가 새것) ssh는 살아 있으면, 전달을 거친 미러 요청이 실패한다(전달 너머의 옛 포트가 연결을 거부해 끊기거나, 같은 포트면 옛 키에 401). 미러가 재시도 구간(10초) 동안 다시 묻고도 실패하거나 401을 받으면 원격 클라이언트가 그 SSH 연결을 끊김으로 두고 앱에 알리고(`ClientOptions::ssh_lost`, MC-40), 앱은 위와 같은 다시 연결(같은 간격, 같은 멈춤 조건)을 탄다: ssh로 새 일회용 코드와 포트를 받고, 포트가 바뀌었으면 옛 전달을 닫고 새 포트로 전달을 연 뒤 페어링해 미러를 다시 잇는다. 누를 것이 없다. 사람의 **연결 끊기**·연결 지우기·머신 지우기, 실패한 연결·새로고침(다시 연결의 시도 포함), 앱 종료 중에는 알리지 않는다(403은 이 호스트에서 출처·상대가 틀렸다는 뜻이라 알리지 않는다). 다시 연결로 돌아온 뒤 120초(가장 긴 간격) 안에 또 끊기면 첫 간격이 아니라 돌아오게 한 간격의 다음부터 이어 가고, 마지막 간격을 지나면 더 시도하지 않는다(사람의 연결은 그대로 된다).
- **버전**: 서버(또는 설치된 앱)의 버전이 이 앱과 다르면(`0.6.0+빌드`와 `v0.6.0 (abc)`는 같은 것으로 본다) **원격 서버 업데이트**가 나온다. 위 설치 단계를 그대로 하고, 실행 중인 서버를 그 앱의 CLI로 멈춘 뒤 바꾼다. 창을 연 Mighty Code가 그 Mac에서 돌고 있으면 확인 창이 닫힌다고 알린다.
- **서버 지우기**(확인 뒤): 연결을 지우고 전달을 닫은 다음, 설치된 앱의 CLI로 서버를 멈추고 `~/Applications/MightyCode.app`을 지운다. 멈추지 못하면 지우지 않는다. 그 Mac의 데이터 폴더는 남긴다. `/Applications`의 앱은 우리가 설치한 것이 아니라서 바꾸거나 지우지 않는다(업데이트는 `~/Applications`에 새로 설치하고, 확인은 홈의 앱을 먼저 본다).
- **표시**: 설정의 연결 목록과 사이드바의 서버 줄은 `ssh:<id>` 대신 `ssh · <대상>`을, 연결 방식 배지는 "SSH"를 보인다.

### 한계와 후속

- 원격 git 변경(diff) 보기(편집기의 HEAD 비교), 마이티 오케스트레이션(위임 자식), 비교 실행, 창 갈라내기, ACP 에이전트는 아직 없다. 창 worktree와 작업 지도는 MC-47부터 된다(위). 로그인 셸은 MC-40부터 fish·csh·tcsh도 된다.
  - **창 worktree의 한계(MC-47)**: 준비·정리 명령은 ssh 연결이 끊기면 이 컴퓨터에서는 실패(-1)로 끝나고 그 머신에서는 계속될 수 있다(붙잡아 두지 않는다). 명령의 값(`worktree.env`, PORT 등)은 에이전트 실행처럼 원격 명령줄에 잠깐 실린다. 그 머신에서 듣는 포트를 읽지 못하면(도구가 없음) 블록은 이미 준 블록만 피한다. 앱을 끈 사이 그 머신에서 지워진 worktree의 포트 블록은 시작할 때 정리되지 않는다(로컬 경로가 아니라서). 홈이 링크 너머면 `pwd -P`한 경로를 루트로 쓴다. 머지 전 점검의 PR·CI 부분은 읽지 않는다. 원격 `git push`의 자격 증명은 그 머신의 것이고 묻지 않는다(`GIT_TERMINAL_PROMPT=0`). 원격 git 한 번이 ssh 한 번이라 병합 하나가 ssh 10여 번이다(Mac은 공유 연결, Windows는 매번 새 연결이라 느리다).
  - 원격 요청 검토는 git이 있는 머신에서만 된다(없으면 스냅숏이 없고 검토 단추가 나오지 않는다). 직접 실행으로 물러난 실행(붙잡기 실패)과 셸 명령 창의 명령은 스냅숏이 없다. 저장소 밖의 큰 폴더(파일 20,000개 초과)도 없다. 스냅숏은 git이 무시하는 파일을 담지 않는다(로컬 MC-18과 같다). 첫 스냅숏은 그 폴더를 한 번 다 읽으므로 시작이 늦을 수 있다(시작 제한 120초).
- 붙잡아 둔 실행: 원격 시스템이 세션이 끝날 때 사용자 프로세스를 모두 끝내도록 설정돼 있으면(systemd-logind `KillUserProcesses=yes`) 연결이 끊길 때 CLI도 끝난다(tmux도 같다). 앱을 다시 켠 뒤 데몬이 가진 붙기로 이어 받은 실행은, 그 뒤 연결이 끊기면 다시 붙지 않고 오류로 끝난다(원격 CLI는 계속). fish·csh 로그인 셸에서는 `PATH`만 넘어오고 그 셸의 다른 환경 변수(API 키 등)는 CLI에 가지 않는다.
- **원격 서버**: 위의 [Mighty Code 서버](#mighty-code-서버-원격-mac-mc-33)로 원격 Mac에 앱 전체를 창 없이 설치·업데이트하고 미러로 붙는다. Linux·Windows 원격 서버는 없다(빌드 없음). 최소 모드에서도 MC-40부터 에이전트 실행은 끊김을 넘어 이어지고(붙잡아 둔 실행), 파일 창에서 저장할 수 있다.
- **확인하지 못한 것**: 실제 원격 Mac에서의 설치·시작(특히 ssh 세션에서 띄운 앱이 그 사용자의 화면 세션의 WindowServer에 붙는지), 실제 `codesign` 검증, ControlMaster 위의 서버 전달과 그 해제는 실제 호스트로 확인하지 않았다(검사는 가짜 ssh와 루프백으로만 한다).
